# Правила работы с Git и Pull Request

## 1. Ветки и Pull Request

Рекомендуемая модель:

- `main`/`master` — защищённая ветка.
- Любая рабочая задача выполняется в отдельной feature-ветке.
- Изменения в `main` попадают только через Pull Request.
- Для merge нужен минимум 1 approval от другого участника команды.
- Перед merge CI должен быть зелёным.
- При необходимости команда может использовать git flow.

## 2. Именование веток

Формат: **тип + номер тикета**.

Примеры:

- `feat/SCRUM-11-neuroreview`
- `fix/SCRUM-25-auth-timeout`
- `docs/SCRUM-31-api-guidelines`

## 3. Commit message

Используем подход **Conventional Commits**:

- `feat`
- `fix`
- `refactor`
- `docs`
- `test`
- `chore`

Для текущего процесса в команде: **сообщения коммитов пишем на русском языке**.

В каждом commit message обязательно указываем ключ задачи Jira, чтобы работали smart commits и связка коммитов с задачами. Ключ задачи должен быть в subject, например `SCRUM-11`.

Примеры:

- `feat: SCRUM-11 добавить авторизацию по токену`
- `fix: SCRUM-25 исправить гонку при обновлении профиля`
- `docs: SCRUM-31 описать требования к ревью`

## 4. Минимальные требования к CI/CD

Обязательный pipeline:

- проверка форматирования и линтера;
- запуск тестов;
- сборка проекта.

Желательно:

- автодеплой в staging;
- автогенерация документации;
- проверка безопасности зависимостей.

## 5. Минимальные требования к тестам

Минимум:

- unit-тесты на ключевую бизнес-логику;
- минимум 1 интеграционный тест (если есть API/БД).

Желательно:

- e2e-тест для основного пользовательского сценария;
- автоматический запуск тестов в CI.
